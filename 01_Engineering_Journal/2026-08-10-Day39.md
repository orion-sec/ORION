## 1. Objective

Today's objective was to move ORION beyond investigation-scoped evidence collection and introduce controlled environment-wide searching.

The goal was to allow ORION to:

1. Extract important entities and indicators from an investigation.
2. Convert those entities into reusable correlation pivots.
3. Search the wider Microsoft security environment for related activity.
4. Preserve separation between independent investigations.
5. Expand an investigation without performing uncontrolled tenant-wide searches.

This establishes the foundation for automated blast-radius analysis.

---

## 2. Architecture Added

The investigation flow now supports:

Incident / Evidence
        ↓
Entity Extraction
        ↓
Entity Correlation
        ↓
Correlation Keys
        ↓
Environment Search
        ↓
Related Security Telemetry
        ↓
Investigation Expansion

The main correlation pivots implemented are:

- User
- IP address
- Device / Host
- File hash
- Domain
- URL

These pivots allow ORION to move from:

"What happened in this alert?"

towards:

"Where else does this entity or indicator appear in the environment?"

## 3. Entity Correlation Engine

Created:

`correlation/entity_correlator.py`

The correlator accepts investigation evidence and extracts security-relevant entities.

Examples include:

User:
`samuel@oriondefense.ai`

IP:
`185.10.20.30`

Device:
`ORION-LAPTOP-01`

SHA-256:
`aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`

Domain:
`malicious-example.com`

URL indicators are also supported.

The correlator produces normalized `correlation_keys` that can be consumed by the environment-search layer.

Example conceptual structure:

{
    "type": "ip",
    "value": "185.10.20.30"
}

This decouples entity discovery from the underlying telemetry provider.

---

## 4. Environment Search Provider

Created:

`providers/environment_search_provider.py`

This provider acts as ORION's environment-search abstraction layer.

It accepts correlation keys and routes them to the appropriate telemetry search.

Current supported search pivots include:

- User → sign-in activity
- IP → sign-in/activity telemetry
- Device → device/security activity
- File hash → Microsoft Defender endpoint telemetry
- Domain → domain-related security telemetry
- URL → URL-related security telemetry

This gives ORION a single search interface while allowing different telemetry sources and KQL queries underneath it.

---

## 5. File Hash Investigation

File-hash searching was added and validated.

ORION can take a SHA-256 indicator discovered during an investigation and pivot into Microsoft Defender endpoint telemetry to determine whether the same file/hash appears elsewhere.

Validation was added for invalid hash lengths to prevent malformed searches.

This is important for future malware blast-radius investigations.

## 6. Domain Investigation

Domain extraction and routing were added.

Example correlation key:

ORION can route this indicator into domain-related telemetry searches.

This is particularly useful for:

## 7. URL Investigation

URL correlation and environment-search routing were implemented.

Potential use cases include:

## 8. Investigation Isolation

An important architectural change was made around sign-in evidence collection.

ORION should not automatically perform an unfiltered tenant-wide sign-in collection for every investigation.

Instead:

Investigation-scoped evidence is preserved first.

Additional telemetry is discovered through controlled correlation pivots.

This prevents unrelated security events from being accidentally merged into the same investigation.

## 13. Troubleshooting / Engineering Lessons

Several issues were encountered and corrected.

### Ruff Import Validation

Unused imports and import-order violations were identified by Ruff.

These were corrected and the affected files were revalidated.

### MagicMock / MSAL Initialization

An EnvironmentSearchProvider test initially instantiated the real provider with:

`config=MagicMock()`

This caused the provider constructor to initialize:

EnvironmentSearchProvider
→ AzureMonitorClient
→ GraphAuthenticator
→ MSAL ConfidentialClientApplication

MSAL attempted to parse the mocked authority URL and failed because the value was a MagicMock rather than a valid URL.

The test was corrected so that the environment-search routing behaviour could be tested without initializing real Microsoft authentication.

Engineering lesson:

Unit tests should isolate the component under test and avoid unnecessary external authentication/network initialization.
